Security Policy

Last updated: 4 September 2026

This Security Policy describes how AD Lab Development secures the Atlassian Forge app Ticket Quality Auditor (the “App”).

1. Platform

The App runs entirely on Atlassian Forge. Core product logic, storage, and optional AI inference use Atlassian-hosted services (Forge functions, Forge app storage / KVS, and Forge LLMs). The App is designed for Runs on Atlassian eligibility: no third-party AI egress and no Remotes/Connect backends for core functionality.

2. Authentication and authorization

  • Access is granted through the customer’s Atlassian Cloud install of the App
  • API calls use Forge’s installation identity (asApp)
  • User-initiated actions call the Forge Authorize API before asApp() Jira access
  • Configuration is managed from the App’s admin UI by Jira administrators
  • Customers are never asked for Atlassian passwords or shared API secrets

3. Permissions (scopes)

  • read:jira-work — read issue content and receive issue events
  • write:jira-work — apply confirmed ticket improvements
  • storage:app — persist configuration and analysis results

4. Data handling

  • Analysis and configuration are stored in Forge app storage (installation-scoped)
  • When AI is enabled, selected ticket text is processed by Atlassian-hosted Forge LLMs
  • When AI is disabled, analysis is deterministic only
  • No separate customer database outside Atlassian for core App state

5. Logging

The App emits structured operational logs with secret redaction. Logs remain within Atlassian Forge logging. We do not share logs containing End-User Data with third parties.

6. Network egress

The App does not define customer-managed egress for core functionality and does not expose remote REST APIs for third-party integration. There is no third-party AI egress.

7. Vulnerability reporting

Report suspected security issues to security@adlabdevelopment.com. Include enough detail to reproduce the issue. Avoid sending production secrets in clear text.
